MBO Rewards Client API

Developer documentation for authenticating, retrieving assigned campaigns, reading performance, accessing payable statements, submitting withdrawal requests, and tracking payments.

API Versionv1
AuthenticationClient ID + API Key
Productionapi.mbo-rewards.com
Sandboxsandbox-api.mbo-rewards.com

Getting Started

Recommended integration sequence for a new client.

1
Get Credentials

Use the Client ID and environment-specific API key from Profile → API & Integration.

2
Test in Sandbox

Authenticate against the Sandbox base URL and confirm campaign retrieval.

3
Integrate Core APIs

Use Campaigns and Performance first, then Statements, Withdrawals, and Payments as needed.

4
Move to Production

Switch to Production credentials and base URL only after integration validation.

MBO Standardization Layer

All network-specific data is normalized before it reaches the Client API.

Network APIs
Impact · Partnerize · Optimise · Trackier · vCommission · Boostiny
→
MBO Canonical Layer
Normalize values, statuses, IDs and money
→
Client API
Stable, client-safe contract
Clients never need to understand individual network schemas. Adding a new network should not require a breaking change to the public MBO Client API.

Every request is authenticated using the client account and its API key.

Example

GET /v1/campaigns HTTP/1.1 Host: api.mbo-rewards.com X-MBO-Client-ID: CLI-HDFC-001 X-MBO-API-Key: mbo_production_sk_xxxxxxxxxxxxx Accept: application/json
Production and Sandbox credentials are separate. A Sandbox key must not authenticate against Production, and a Production key must not authenticate against Sandbox.

Returns only campaigns available to the authenticated client account.

Use this API when: your application needs the latest campaigns available to your account.
The API never returns network/source information, raw network commission, MBO margin, network campaign IDs, or internal source-selection logic.

Use this API when: your application needs reporting for clicks, orders, sales, and commission.
Performance responses never expose network clicks, network order IDs, network conversion IDs, raw network status, network commission, or MBO margin.

Common API Standards

Shared rules applied consistently across all MBO Rewards client API endpoints.

STANDARDResponse Envelope

Successful API responses use data as the primary payload key. List responses may also include pagination. Errors use the separate error envelope.

{ "data": {...}, "meta": { "request_id": "req_01HDFC8F4K", "api_version": "v1" } }
STANDARDPagination

List endpoints use page-based pagination.

ParameterDefaultRule
page1Positive integer.
page_size25Recommended maximum: 100.
{ "pagination": { "page": 1, "page_size": 25, "total_records": 284, "total_pages": 12 } }
STANDARDFiltering

Filters are optional unless explicitly marked required by the endpoint.

Filter TypeFormatExample
Date rangeYYYY-MM-DD?from_date=2026-08-01&to_date=2026-08-16
StatusUppercase enum?status=PAID
Campaign TypeUppercase enum?campaign_type=COUPON

SearchFree text?search=Nike
Unknown filter values should return a validation error rather than being silently ignored.
STANDARDDate & Time
Field TypeFormatExample

Where the product UI stores date and time separately, the API may also return separate last_updated_date and last_updated_time fields. If a source does not provide a time value, the API should return null rather than inventing one.
STANDARDMoney & Currency

Monetary values use a consistent amount/currency object.

{ "amount": 530.00, "currency": "USD" }
RuleDescription
AmountNumeric value, not a formatted string.
CurrencyISO 4217 currency code such as USD, INR, or AED.
No mixed currenciesTotals should not combine multiple currencies into one numeric total.
STANDARDVersioning

The API version is part of the base path.

https://api.mbo-rewards.com/v1
Breaking changes require a new version path. Non-breaking additions, such as adding an optional field, may remain within the same version.
STANDARDIdempotency

POST requests that create a financial object should support an idempotency key.

HeaderRequiredDescription
Idempotency-KeyRecommended for financial POSTsUnique client-generated key used to prevent accidental duplicate creation.
POST /v1/withdrawal-requests Idempotency-Key: hdfc-withdrawal-2026-08-001
Reusing the same idempotency key with the same request payload should return the original result. Reusing the key with a different payload should return a conflict error.
STANDARDRate Limits

Exact production limits can be configured later, but the response contract should be standardized now.

HeaderDescription
X-RateLimit-LimitTotal requests allowed in the current window.
X-RateLimit-RemainingRequests remaining in the current window.
X-RateLimit-ResetUTC timestamp when the limit resets.
Retry-AfterSeconds to wait after a 429 response.
The exact numeric limit should be set during infrastructure implementation rather than invented in the documentation prototype.
